# Data Reconciliation Engine

> **Enterprise-grade, 4-tier financial transaction reconciliation pipeline built with DuckDB, Pandas, and Pydantic v2.**

---

## Pipeline Architecture

```
         ┌──────────────────────────────────────────────────────┐
         │               Data Reconciliation Engine              │
         └──────────────────────────────────────────────────────┘

  [source.csv] ──┐
                 ├──► [generator.py] ──► [source.csv / target.csv / expected_truth.json]
  [target.csv] ──┘
       │
       ▼
  [pipeline.py] ──► Load & cast DataFrames
       │
       ├──► Tier 1 ─ Schema & Volume
       │       └─ Column diff │ Row count delta
       │
       ├──► Tier 2 ─ Business Key Completeness
       │       └─ Anti-joins │ Duplicate PK detection
       │
       ├──► Tier 3 ─ Aggregate Metric Reconciler
       │       └─ SUM/AVG/MIN/MAX │ Currency × Status grouping │ Tolerance bands
       │
       └──► Tier 4 ─ Field-Level Attribute Comparator
               └─ Inner join │ IS DISTINCT FROM │ Cell-by-cell diff

  Outputs ──────────────────────────────────────────────────────────
    output/reconciliation_report.json   (machine-readable JSON)
    output/quarantined_mismatches.csv   (actionable quarantine)
```

## Quick Start

### 1. Prerequisites

- Python **3.10+**
- pip

### 2. One-Command Setup & Run (Linux / macOS)

```bash
./run.sh
```

### 2b. Manual Setup (Windows / any OS)

```bash
python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS/Linux:
source .venv/bin/activate

pip install -r requirements.txt

# Generate sample data
python -m src.generator --size 1000 --seed 42 --output-dir data/sample

# Run reconciliation
python -m src.pipeline \
    --source data/sample/source.csv \
    --target data/sample/target.csv \
    --output-dir output

# Run tests
pytest tests/ -v
```

## Data Dictionary

| Column | Type | Nullable | Notes |
|---|---|---|---|
| `transaction_id` | VARCHAR (UUID) | **No** (PK) | Business key; rows with NULL are excluded from set operations |
| `customer_id` | VARCHAR | Yes | Arbitrary customer identifier |
| `transaction_timestamp` | VARCHAR (ISO-8601 UTC) | Yes | Stored as string to capture malformed values explicitly |
| `amount` | DOUBLE | Yes | Monetary value; cast to float for aggregation |
| `currency` | VARCHAR | Yes | Controlled vocab: `USD`, `EUR`, `INR`, `GBP` |
| `status` | VARCHAR | Yes | Controlled vocab: `COMPLETED`, `PENDING`, `FAILED`, `REFUNDED` |

## Reconciliation Tiers

| Tier | Name | What It Checks |
|---|---|---|
| 1 | Schema & Volume | Column names, data type catalog, total row count delta |
| 2 | Key Completeness | Missing IDs (source→target), orphan IDs (target-only), duplicate PKs |
| 3 | Aggregate Metrics | SUM/AVG/MIN/MAX per currency, per status, per currency×status; floating-point tolerance |
| 4 | Field Attributes | Cell-by-cell comparison of all non-key columns using null-safe `IS DISTINCT FROM` |

## Anomaly Injection Rates

| Anomaly Class | Default Rate | Description |
|---|---|---|
| Missing rows | 2% | Source records dropped from target |
| Orphan rows | 1% | Target-only phantom records |
| Cell discrepancies | 3% | Amount inflated or status changed |
| Duplicate keys | 1% | Duplicated PKs in source & target |
| Malformed records | 1% | Null PK or invalid timestamp |

## Performance Benchmarks

Measured on this machine (Intel Core i7 / 16 GB RAM / Windows 11, DuckDB in-memory):

| Dataset Size | Engine | Empirical Elapsed Time |
|---|---|---|
| **1,000 rows** | DuckDB in-memory | **~0.32s** |
| **100,000 rows** | DuckDB in-memory | **~4.44s** |
| ~10M rows | DuckDB (disk-spillable) | ~45–90s (estimated) |
| 100M+ rows | Apache Spark on cluster | Minutes (horizontally scalable) |

> Times include data load, all 4 reconciliation tiers, JSON report write, and CSV quarantine flush.

### DuckDB Columnar Optimization

The engine exploits DuckDB's **vectorized execution model** for two critical operations:

| Operation | DuckDB Approach | Naïve Python Alternative |
|---|---|---|
| Key completeness (Tier 2) | `NOT EXISTS` sub-select → hash-join anti-join executed in columnar batches | `df[~df['id'].isin(other['id'])]` → full sort-merge or row-by-row loop |
| Cell-level comparison (Tier 4) | `IS DISTINCT FROM` evaluated over all columns in a single scan using SIMD-vectorized comparators | Python `iterrows()` → 1 Python call per cell per row |

DuckDB's columnar engine processes data in **2048-row vectorized batches** (its `STANDARD_VECTOR_SIZE`), keeping hot data in CPU L2/L3 cache. This yields **10–50× throughput** over row-iteration for aggregate and comparison workloads.

### Scale-Out Migration Path

| Data Volume | Recommended Engine | Rationale |
|---|---|---|
| < 1M rows | DuckDB in-memory (this engine) | Sub-second, zero infra |
| 1M – 10M rows | DuckDB with disk spill | Automatic, no code change |
| > 10M rows (exceeds RAM) | **Migrate to PySpark** | RAM exhaustion causes swap thrashing; Spark distributes across nodes |
| Streaming / real-time | Apache Flink or Spark Structured Streaming | DuckDB has no native stream ingestion |

**Migration trigger:** When your dataset routinely exceeds available node RAM (typically > 10M–50M rows on a 16 GB machine), migrate from embedded DuckDB to:

1. **MotherDuck** (cloud DuckDB) — zero-code migration, scales to ~500M rows with serverless billing  
2. **PySpark** — replace `duckdb.connect()` calls with `SparkSession.builder`; anti-join logic maps directly to `DataFrame.subtract()` and `join(..., how='left_anti')`; aggregate logic maps to `groupBy().agg()`

## Design Trade-offs: DuckDB vs. Distributed Systems

| Dimension | DuckDB (this engine) | Apache Spark |
|---|---|---|
| Dataset limit | ~RAM size (8–64 GB typical) | Petabyte-scale |
| Setup complexity | `pip install duckdb` | Cluster + JVM + YARN/K8s |
| Developer UX | Python-native, SQL | PySpark API, Java debugging |
| Small-data latency | Sub-second | 10–30s cluster bootstrap |
| Infra cost | Zero | EC2/GKE cost |
| Streaming | Not native | Spark Structured Streaming |
| Migration path | → MotherDuck (cloud DuckDB) or → Spark | N/A |

**Migration trigger:** Migrate from DuckDB to Spark when:
1. Dataset routinely exceeds available RAM (>50 GB)
2. Multi-tenant parallelism required (concurrent reconciliation jobs)
3. Real-time streaming reconciliation needed
